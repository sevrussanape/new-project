# Architecture

```text
Browser UI (web/index.html)
        |
        | loopback HTTP / JSON
        v
studio.py (local server + API)
        |
        v
hardware_scanner.py
        |  read-only GPU / VRAM / RAM / disk / CUDA inventory
        v
model_selector.py
        |  only integrated adapters; shared eligibility policy
        v
engine/job_manager.py
        |
        v
engine/video_engine.py
        |-- LTXRuntime: PyTorch + Diffusers (only integrated generative adapter)
        |-- Image Motion: Pillow + imageio-ffmpeg (non-generative renderer)
        |
        v
outputs/*.mp4 → browser preview
```

## Design decisions

- One local Python process owns the web API and job queue; there is no second workflow/model server.
- The hardware scanner is side-effect free: it reads GPU, VRAM, driver, temperature, utilization, RAM, disk and optional PyTorch CUDA facts.
- The model selector recommends only models with a registered, implemented runtime adapter.
- The UI/API advisor and inference engine use the same selector policy. The engine repeats the check immediately before model loading.
- Unknown free VRAM is unsafe, not assumed sufficient.
- Jobs run sequentially to reduce VRAM pressure. Jobs expose status, progress, cancellation and output path.
- Image Motion is explicitly non-generative and cannot be substituted for an AI video request.
- Package installation and model downloads are explicit or lazy first-use actions, not side effects of scanning.

## LTX runtime boundary

LTX is loaded lazily with Diffusers. The runtime uses CUDA only, chooses BF16 when PyTorch reports support and otherwise FP16, enables group offload and VAE tiling when available. This build uses a 10 GB total / 8.5 GB free VRAM gate, 32 GB system RAM and 50 GB free disk. The default generation profile caps scene clips at 4 seconds, 12 FPS, 512-pixel long edge and 20 denoising steps.

Passing these checks is not a guarantee of inference success. Driver, CUDA/PyTorch version, GPU architecture, model revision and available resources must be validated on the actual PC.

## HTTP and file safety

The server binds to loopback. Uploaded image/audio data is size-limited and validated before being written under `uploads/`. Output names are generated by the server; clients cannot choose arbitrary filesystem paths. Project timeline retrieval validates the job identifier and confines access to the outputs directory.
